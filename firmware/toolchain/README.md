# firmware/toolchain/

The repository-level scripts around the firmware: what builds a module or a pack, what assembles a console page, and the `check_*.py` that CI runs. Each script's docstring is its manual (`python firmware/toolchain/<script>.py --help` or the top of the file); this page only says which is which. (`../patternflow/toolchain/` is a different thing: PlatformIO `extra_scripts`, which must stay sketch-relative.)

**Building things.** `build_module.py` compiles a module folder into a `.pfm` with the Xtensa toolchain; `port_preset.py` turns a curated preset header into a module folder; `make_pack.py` bundles built modules into the shareable Basics pack. `build_clock_glyphs.py` generates the clock feature's digit glyphs. `release.py` is the two-command release (cut, publish) described in [`docs/RELEASING.md`](../../docs/RELEASING.md).

**Console pages.** The device serves each console page from a C string literal in a header. `console_pages.py` splices `../patternflow/console/*.html` into those headers (`build` to regenerate, `check` in CI). One page is not written as a page: `/audio-in` is assembled by `build_audio_in_page.py` from the audio extension's mapping editor in `tools/patternflow-audio-extension/` and the panel's own half in `../patternflow/console/_audio_in_*`, with comments and indentation dropped on the way. `console_pages.py build` runs that step first, so one command regenerates everything; `console_pages.py check` and `build_audio_in_page.py --check` fail when the generated page is not what its sources assemble to, or is over its size budget (`BUDGET` in the script: bytes gzipped, as the panel sends the page). `console_serve.py` previews the pages locally against a mock panel, assembling `/audio-in` from its sources on every request; its audio endpoints are a port of the firmware's handlers, with `/mock?audio=<state>` choosing what the panel hears, and when a handler in `features/audio_in/` or `features/audio/` changes that port changes with it. How to edit a page is [`../patternflow/console/README.md`](../patternflow/console/README.md).

**The guide's live demos.** `console_demo.py` writes the core console as static files to `web/public/guide/console-demo/` for the Play guide's console window, wired to a fake device; `editor_demo.py` does the same for the audio extension's mapping editor in the Audio guide (`web/public/guide/audio-editor/`). Both take `--check`. Neither runs in CI or in `release.py`: the release checklist in [`docs/RELEASING.md`](../../docs/RELEASING.md) says when to run them, because the console demo carries the version and build it presents.

**Checks.** These are what `firmware-checks.yml` runs on every pull request that touches the firmware, and what you run before pushing:

- the boundary rule — `check_boundaries.py`: the core references no feature, no feature flag, no feature name on a core page (the rule itself is [`docs/EDITIONS.md`](../../docs/EDITIONS.md));
- the frozen host ⇄ module ABI — `check_abi_freeze.py`, `check_module_elf.py`;
- the module SDK's inline libm — `check_libm.py` and `check_module_libm.py`: `abi/pf_libm.h` puts inline code behind `floorf`, `fmodf` and five others in every `.pfm`, on the claim that each returns the libm result bit for bit. `tests/libm_test.cpp` holds the seven to that: every one of the 2^32 floats through the one-argument functions and about three billion comparisons through the rest, against the libm of the machine running it; it takes a minute or two. What a PC cannot compile is the half of the header only a module build has, so `check_module_libm.py` builds `tests/modules/_libm_shapes` with the Xtensa compiler and reads the object: every spelling the header claims is inline, with the library call left only as its fallback. It needs the toolchain, and CI runs it in the firmware build job. What the two hold is the seven functions; a rebuilt pattern's own arithmetic can still differ in its last bit, because `-O2` and inline code move where GCC fuses `a*b+c` (`abi/pf_libm.h` says where that shows);
- the preset twins — `check_presets.py`: `web/src/lib/presets/` and `../patternflow/presets/` stay in step, with the deliberate exceptions listed inside it;
- versions — `check_versions.py`: the version the firmware reports, the editions, `AGENTS.md`, the flasher manifest and the shelf all agree;
- images — `check_footprint.py` (each composition's size against its baseline; it needs the built image, so it runs in `firmware-build.yml` after each composition compiles, as `check_module_libm.py` does);
- host-side unit tests of pure engine code — `check_math.py`, `check_blit.py`, `check_oe.py`, `check_send.py`, `check_thumbs.py`, `check_runtime.py`, `check_crash.py`, `check_network.py`, `check_midi.py`, each compiling and running its twin in `tests/` (`*_test.cpp`) natively, with `--sanitize` for ASan/UBSan;
- the vendored web server — `check_parser.py`: the real `src/webserver/Parsing.cpp` against a scripted socket and a fake clock, failing on a wait that does not sleep or does not end. Its `KNOWN:` lines are what the parser does today that the test would otherwise fail, pinned so that fixing one turns the check red until the pin is removed;
- `check_sources.py`, a fast pre-compile sanity pass.

`tests/` also holds `modules/_ctor_probe/`, a module that exists only to exercise the loader's `.init_array` path; build it with `build_module.py` and inspect the ELF as its header comment says. Beside it, `modules/_crash_probe/` writes through a null pointer from `draw()` when a knob moves: the bench case for the crash record in `/api/status`. And `modules/_hang_probe/` is a module whose `draw()` stops returning eight seconds after it is picked - the bench tool for "the console outlives a hung render loop" (`src/core_loop_sync.h`), which no well-behaved pattern can show. With K1 or K2 turned while it counts down the stop ends after thirty or twenty seconds, for the other half: what the loop does when it comes back to requests that gave up on it. Its header comment has the three commands. `modules/_math_probe/` is the on-board half of `check_libm.py`: it runs the SDK's inline `floorf`/`fmodf` and the firmware's own libm side by side for 1.3 s in `setup()` and puts the verdict in its own name (`"active": "math ok 9/9 ..."` in `/api/status`), then keeps comparing every frame, green or red. It is how to tell that a board's FPU does what the PC proof assumes - above all that its multiply-subtract is fused.

`module.ld` is the linker script every `.pfm` is linked with.
